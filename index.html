Chapter One

什么是绑核
为什么要绑核

绑核不是一个孤立的 taskset 命令。它是在 Linux 调度、NUMA 内存和设备 I/O 路径之间，为关键执行实体建立稳定的资源边界。

CHAPTER 0103
01 · Definition

绑核 = 限定“谁可以在哪些 CPU 上运行”

01 / 01
CPU affinity 是调度器的约束条件，不是把线程永久焊死在某个物理核上。 Linux 仍负责在允许集合内调度；绑核改变的是可选 CPU 集合，从“整机任意 CPU”收缩到“指定 CPU 或 CPU pool”。
PROCESS

进程级 affinity

taskset -acp 2-37 PID 同时设置进程及其线程的允许 CPU 集合，适合先给 worker 建立大边界。

THREAD

线程级 affinity

taskset -cp 38 TID 进一步把特定运行时线程放到专用 CPU，避免与 worker 主路径争抢。

INTERRUPT

IRQ affinity

写入 /proc/irq/<irq>/smp_affinity，决定设备中断由哪些 CPU 处理；这不是进程线程，但同样会消耗 CPU 时间。

关键词：sched_setaffinity / cpuset / PID / TID / IRQ04

一次迁移带来的真实成本

  • 排队：目标 CPU 上可能已有其他 runnable 线程。
  • cache 失温：工作集需要重新进入目标 CPU 的 L1/L2，甚至 LLC。
  • NUMA 漂移：线程迁走了，但内存页仍可能留在原 NUMA node。
  • 尾延迟放大：单次成本不一定大，但在短周期高频主循环中会累积为 jitter。

01 · NUMA

CPU 在本地，内存却在远端：只绑线程还不够

01 / 03
NUMA 0

CPU 0-47 + Memory 0

worker 被绑定在这里，访问本地页路径更短。

NUMA 1

CPU 48-95 + Memory 1

若热页仍在这里，worker 每次访问都要跨 socket / interconnect。

线程 affinity 只限制“在哪运行”；内存 locality 还要看页面实际落在哪个 NUMA node。
完整的 NUMA 优化包含两件事：CPU placement 与 memory placement。

vLLM Ascend 的处理

先给 worker 和关键线程设置 affinity，再使用 migratepages PID source_nodes target_node 将进程已有页面迁移到 CPU pool 所在 NUMA node。

# 示例：把 PID 4201 的页面从 NUMA 0,1,2,3 迁到 NUMA 1 migratepages 4201 0,1,2,3 1
NUMA locality = CPU pool 所在节点 + 内存页所在节点06

01 · Contention

多 worker 共享同一 cpuset，最危险的是“看似都能用，实际互相重叠”

01 / 05
BAD · LOCAL VIEW

每个进程只按“自己可见的 NPU”切 CPU

Process A: visible NPU = [0] allowed_cpus = 0-79 → NPU0 gets 0-79 Process B: visible NPU = [1] allowed_cpus = 0-79 → NPU1 gets 0-79 结果：两个 worker 完全重叠
GOOD · GLOBAL VIEW

按全局 logical NPU ID 建立确定性分区

total_logic_npus = 2 allowed_cpus = 0-79 NPU0 → 0-39 NPU1 → 40-79 结果：不同进程得到相同、无重叠的计算结果
好的绑核策略必须对“独立进程、相同 cpuset、不同可见 NPU”仍然给出无冲突结果。
这正是 global_slice 与 hidden-NPU 参与分配要解决的问题08
01 · Outcome

绑核优化的是主机侧可预测性，不是模型数值与 NPU 峰值算力

01 / 06
BENEFIT 01

减少调度迁移与抢占

关键线程在稳定 CPU pool 内运行，降低与其他服务、其他 rank 和 runtime 线程的竞争。

BENEFIT 02

降低远端 NUMA 访问

CPU placement 与 memory migration 配合，减少跨 NUMA 读写带来的额外延迟。

BENEFIT 03

改善尾延迟与多卡隔离

减少偶发 host-side stall，让吞吐和 P99/P999 更可预测。

更容易见效：CPU 负载高、短请求、多个 worker / DP 组、跨 NUMA、宿主机有其他服务竞争。
不会直接修复：NPU 算子慢、HCCL 通信瓶颈、模型调度策略不合理、显存不足、业务排队过长。
结论：先确认瓶颈在 host scheduling / locality，再评价绑核收益09

02 · Global Slice

global_slice：用全局 NPU ID 计算确定性 CPU 分片

02 / 06
# 核心公式
base  = len(allowed_cpus) // total_npus
extra = len(allowed_cpus) % total_npus

start = npu_id * base + min(npu_id, extra)
take  = base + (1 if npu_id < extra else 0)

pool  = allowed_cpus[start : start + take]

total_npus 的优先级

① npu-smi info -m 得到的全局 logical NPU 数；② topo affinity 条目数；③ 当前 running NPU 数。

为什么不能按 visible 数量切

每个独立 worker 的 visible 集合可能不同，但它们共享 cpuset。全局 ID 让每个进程独立计算时仍得出同一个 NPU → CPU 映射。

640 CPUs / 16 logical NPUs → base = 40, extra = 0 NPU0 = CPU 0-39 · NPU1 = CPU 40-79 · ... · NPU15 = CPU 600-639
A3 默认使用 global_slice；NUMA locality 依赖 CPU 编号与 cpuset 布局是否对齐16

约束调度

限制 worker 与关键线程的 allowed CPU 集合，减少迁移、抢占与共享竞争。

尊重拓扑
