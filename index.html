System View

系统级绑核设计

绑核不是把一个 PID 固定到几个 CPU 这么简单。这里先讲系统级原理，再落到 vllm-ascend 的实现：DeviceInfo 采集信息，CpuAlloc 建池和绑定，不同 Ascend 产品按不同策略处理。

学习目标：能解释为什么绑核有效、什么时候收益最大、什么时候反而危险。
工程目标：让 worker、runtime 线程、IRQ/polling 和系统噪声各在合理位置，减少 host-side 抖动。
Key takeaway：绑核优化的是确定性，不是 CPU 峰值算力。

Map

绑核是一条跨层链路

一次推理请求会在用户态调度、runtime API、驱动队列、设备执行、完成事件和内存访问之间反复穿梭。只看某个线程的 affinity，很容易忽略真实瓶颈来自系统链路中的哪一段。

硬件层CPU core、SMT、NUMA node、cache、内存控制器、PCIe/HCCS 距离决定访问成本。
OS 层Linux scheduler 根据就绪队列、负载、优先级、affinity 和 cgroup 边界选择实际 CPU。
Runtime 层worker、ACL、通信、release、callback、polling、driver helper 不一定有相同的绑核诉求。
判断绑核方案是否合理，要从“线程在哪跑、访问哪块内存、服务哪个设备、是否会互相抢占”四个问题同时看。
从系统链路看绑核02
Goal
绑核的目标不是让 CPU 更快，而是让关键路径更稳定。

如果瓶颈在 device compute，绑核可能收益很小；如果瓶颈在 host 调度、队列提交、事件处理、内存访问和线程抢占，绑核就可能明显提升吞吐稳定性和尾延迟表现。

收益来源： 1. 减少线程迁移，降低 cache 热数据失效概率 2. 减少关键线程与后台线程争抢同一个 CPU 3. 让 worker 靠近亲和 NUMA，减少远端内存访问 4. 让 IRQ / polling / runtime helper 位置更可控
Key takeaway：绑核收益最大的场景通常是 host-bound，而不是纯 compute-bound。
性能优化的对象是 host-side 稳定性03
Hardware Topology

先看机器长什么样

CPU 核、NUMA 节点、内存控制器、PCIe 设备和加速卡不是均匀连接的。一个 CPU 访问本地 NUMA 内存和远端 NUMA 内存，成本可能完全不同；一个设备也常常更靠近某些 NUMA。

NUMA locality：worker 绑在亲和 NUMA，通常更容易减少跨 NUMA 访问。
设备距离：IRQ、polling、提交队列处理线程也应该考虑设备所在拓扑。
策略第一步不是切 CPU，而是确认 CPU/NPU/NUMA 的关系。

Scheduler

绑核是在约束 Linux 调度器

线程不是绝对随机地跑在某个 CPU 上。Linux scheduler 会综合优先级、负载均衡、cache 亲和、NUMA 信息和 affinity mask 做选择。绑核的本质是把“可选 CPU 集合”缩小，让关键线程少漂移。

不绑：调度器自由度大，吞吐平均值可能还行，但抖动更难控制。
绑核：自由度变小，关键线程更稳定，但 CPU 选少了会造成反向拥塞。
绑核不是接管调度器，而是给调度器设置边界。

Memory Path

绑核会改变 cache 和内存访问稳定性

CPU 不只是“执行代码”，它还会反复读写队列、对象、计数器、请求状态、buffer 元信息。线程迁移后，原 CPU 上的 cache 热数据不一定还能命中；跨 NUMA 访问也会增加延迟和抖动。

会被缓存的数据：调度队列、batch metadata、引用计数、状态机字段、环形队列指针。
为什么缓存：CPU 会把近期访问的数据放进 L1/L2/L3，减少每次都去内存拿。
线程位置和 page placement 要一起看，否则“绑了 CPU 但内存还在远端”。

Device Path

加速卡不是孤岛

kernel launch、算子执行、拷贝、图执行请求通常由主路径发起，但真正的执行和完成通知会经过驱动队列、设备队列、中断或 polling。host 端如果处理完成事件不稳定，device 端再快也会被 host 拖住。

SQ：submit queue，host 向设备提交任务或命令的队列。
CQ：completion queue，设备把完成状态带回 host 侧处理。
IRQ/polling 不是“额外概念”，它们是设备事件回到 CPU 的路径。

Isolation

降低抢占概率，靠的是减少竞争者

绑核不会自动提高线程优先级。它降低关键线程被抢占概率的方式，是把普通线程、后台服务、日志、监控、runtime 噪声尽量排除出关键 CPU pool，让关键线程所在 CPU 的就绪队列更干净。

不隔离： CPU set = worker + logging + monitor + runtime helper + system service 结果 = 关键线程经常和普通线程抢同一批时间片 隔离后： worker pool / helper pool / IRQ or polling pool / background pool 结果 = 关键路径更少被无关线程打断
绑核的收益来自“更少竞争”，不是来自“更高优先级”。
CPU isolation 是稳定性的基础09
Policy Design

一套绑核策略至少要走五步

1. 采集收集 allowed CPUs、NUMA、topology、visible devices、线程列表和 IRQ/polling 信息。
2. 建池按设备或 worker 计算 CPU pool，必须考虑 hidden NPU，避免 DP 组重复用 CPU。
3. 分角色区分 main、runtime helper、IRQ、polling、background 和 memory placement。
4. 执行用 taskset、smp_affinity、migratepages 等机制实际改变运行位置。
5. 验证反查 /proc、taskset、interrupts、NUMA 状态和压测结果，确认没有副作用。
6. 回滚设计时必须知道哪些修改是进程级，哪些可能影响宿主机或后台线程。
只会“分 CPU”不够，完整方案必须包含执行、观测和回滚边界。
采集 → 建池 → 分角色 → 执行 → 验证10
vLLM Ascend Entry

vllm-ascend 的绑核入口是一条固定执行链

项目里不是启动时随便 taskset 一下，而是在 worker 初始化后按 rank 执行 `bind_cpus(rank_id)`。入口先判断是否 ARM CPU，再创建 `CpuAlloc`，最后由 `run_all()` 编排完整流程。

bind_cpus(rank_id) └─ is_arm_cpu() └─ CpuAlloc(rank_id) └─ run_all() ├─ build_cpu_pools() ├─ allocate() ├─ print_plan() ├─ bind_threads() └─ bind_npu_irq()
vllm-ascend 的绑核是 worker 进程内执行的：每个 rank 负责自己的 worker 线程、内存迁移和当前 NPU 相关处理。

Ascend 950 Plan

Ascend 950 当前方案：UVB + worker cluster

Ascend 950 的策略和 A2/A3 不同：系统级 `uvb_poll_window_thread` 需要绑定到 NUMA0 可用 CPU；worker 不再拿大段 NUMA CPU，而是按 topo 亲和 NUMA 分配一个 cluster。

Ascend 950 flow: 1. build_cpu_node_map(): 解析 lscpu -e=CPU,NODE 2. bind_uvb_poll_window_threads(): NUMA0 CPUs - CPU0 -> uvb_poll_window_thread 3. get_ascend_950_cluster_size(): Thread(s) per core 1/2 -> 8/16 CPUs 4. build_ascend_950_cpu_pools(): 按 NPU topo 亲和 NUMA 切 cluster 5. _allocate_ascend_950_roles(): main = cluster, acl/release = []
为什么 hidden NPU 参与：多个 DP 组可能共享完整 cpuset，只按 visible NPU 切会重复用 CPU。
为什么不绑 ACL/release：当前 Ascend 950 方案只要求 worker 主路径和子线程绑定到 cluster，ACL/release 不单独分池。

Containers

容器里的绑核先看边界

在容器中，进程看到的 CPU、PID、权限和宿主机不一定一致。你以为在绑整机 CPU，实际可能只能使用 cgroup 分配的一小段；你以为能看到 host 后台线程，实际 PID namespace 隔离后根本看不到。

  • Cpus_allowed_list 是当前进程真实可用 CPU 边界，不能只看物理 CPU 总数。
  • cpuset/cgroup 会限制进程，即使 `lscpu` 显示机器有更多 CPU。
  • PID namespace 会影响能否看到宿主机线程；绑定 host thread 常需要 `--pid=host`。
  • 继承关系 很重要：父进程 affinity 可能影响后续 worker、helper 或后台线程。
容器里调绑核，第一条命令应该是查边界，而不是直接 taskset。
先确认边界，再谈策略17
Risk

错误绑核比不绑更危险

绑核是强约束。约束正确时，它减少不确定性；约束错误时，它会制造新的瓶颈，并且问题往往会伪装成“模型慢”“框架慢”或“机器不稳定”。

过度限制CPU 太少，main/helper/IRQ 互相抢，吞吐和尾延迟都变差。
拓扑错误worker 绑到远端 NUMA，cache 和内存访问更不稳定。
误伤线程把系统级 polling 或后台线程绑错，关闭服务后影响仍可能持续。
隐藏重叠只看 visible NPU 切 CPU，多个 DP 组可能重复使用同一段 CPU。
权限不足写 IRQ affinity、迁移内存、查看 host PID 都可能受权限限制。
观测缺失没有记录变更前后状态，就无法判断收益来自哪里。
错误绑核比不绑更危险18
Observability

专家先看证据，再谈策略

绑核问题不能只看日志里的“plan”。必须反查进程、线程、NUMA、IRQ 和容器边界，确认实际状态等于设计状态。

# 进程/线程 affinity taskset -pc <pid> for t in /proc/<pid>/task/*; do grep Cpus_allowed_list $t/status; done # 容器和 NUMA 边界 cat /proc/<pid>/status | grep Cpus_allowed_list lscpu -e=CPU,NODE numactl -H # 设备事件路径 cat /proc/interrupts ls /proc/<pid>/task/*/comm | xargs -I{} sh -c 'echo {}; cat {}'
验证顺序：先确认能用哪些 CPU，再确认线程实际在哪，最后对比性能。
没有观测，就没有调优19
Benchmark

压测绑核收益，要主动构造 host-bound 场景

如果请求太少，host 线程不忙，看不出收益；如果模型计算太重，瓶颈在 device compute，也看不出收益。要展示绑核价值，应让 host 调度、提交、事件处理和 runtime 线程竞争变成主要压力源。

推荐方向：小输入/中等输出、较高并发、持续压测、request_rate=0 或足够高，让服务端尽量饱和。
必须固定：模型、精度、TP/DP、输入输出长度、并发、warmup、正式测量窗口。
  • 记录开启/关闭绑核前后的 CPU affinity、NUMA、IRQ/polling 和关键线程状态。
  • 每组至少多跑几次，关注 tokens/s、P99 latency 和抖动，而不是只看单次最高值。
  • 关闭绑核后要确认没有遗留 host 线程 affinity，否则基线会被污染。
展示型 benchmark 的目标不是“证明任何场景都涨”，而是找出绑核最该发挥作用的系统压力场景。
测的是系统，不只是一个开关20

Conclusion
系统级绑核 = 拓扑理解 + CPU 隔离 + 角色分配 + 副作用控制 + 可观测验证。
一句话背诵：绑核是用 affinity/cpuset 等机制，把关键线程限制在更合理、更少竞争、更靠近设备和内存的位置。
判断收益：host-bound 越明显，关键线程越容易被抢占，设备事件越依赖 host，绑核越可能有价值。
判断风险：如果拓扑不清、线程角色不清、容器边界不清，绑核可能比不绑更危险。
最终闭环：设计方案必须能被命令观测证明，也必须能安全回滚。

最终判断 绑核不是固定线程这么简单，而是在复杂系统里为关键路径设计稳定的运行边界。
